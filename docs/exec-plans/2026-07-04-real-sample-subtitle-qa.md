# 真实样本字幕 QA 报告

对七月提供的真实产出样本做的只读质量审查。样本：Bilibili 华为 Mate 80 Pro 评测（BV1F7T46wEyT），本地 ASR 产出 `华为Mate 80 Pro性能分析：进步巨大！ [BV1F7T46wEyT].local-asr.en.srt`，469 条，覆盖 25 分钟。

## 结论先行
**时序与分段质量：优秀，无缺口**（客观指标全部健康，验证了"speech 已达人类水平时序"在真实样本上成立）。
**识别内容：一处真实、可量化的瑕疵——数字型号被空格拆开**（`麒麟90 30` 应为 `麒麟9030`），共 113 处。属核心 ASR 层（whisper 分词特征），**未自主修复**（算法层已定型、不在本次体验层范围、有回归风险），作为证据记录供七月决策。

## 一、时序 / 分段质量（客观指标，健康）
| 指标 | 结果 | 判定 |
|---|---|---|
| 条目数 | 469（25 分钟） | — |

结论：时序/分段无需任何修复。这条视频的字幕在"何时出现、显示多久、每行多长、是否重叠"上全部达标。

## 二、识别内容瑕疵（真实、可量化，但属算法层）
- **数字型号空格拆分：113 处**。芯片型号是本视频核心术语，被一致性地拆开：
  - `麒麟90 30`（应 `麒麟9030`）、`90 20`（应 `9020`）
  - `2 75`（应 `2.75`）、`9 000`（应 `9000`）、`1 72`（应 `1.72`）
- **孤立大写字母：48 处**（如 `SoC` → `So C` 类）。
- 之前采样还见 `九牛二虎之力` → `9 妞二虎之力`。

**根因（只读确认）**：来自 Whisper 原始 token 流（数字/子词按空格分隔），项目**无数字规范化后处理**；现有 sub-word 拼接（`observedLatinContinuationPrefixes`，0.8.2 review 调过的那段）只作用于拉丁子词，不管数字序列。

**为何未自主修**：新增"数字/型号合并"是**核心 ASR 层的新能力**，属于本次"只做体验层、不动已定型算法"的排除范围，且 0.8.2 review 刻意锁定了该流水线（改动有识别质量回归风险）。这是需七月决策的算法层改进，不是可自主修的体验层缺口。

**给七月的可执行建议（若日后想改，非本轮）**：
1. 可加一个**受控的数字合并后处理**（在 cue 文本层，非识别层）：合并"数字 空格 数字"为连续数字，但需谨慎——不能误合并"测了 3 台 5 款"这类真实分隔的数字，也不能碰 `Mate 80`/`90 30 Pro` 里型号与后缀的合理空格。建议先做 eval：收集数字拆分样本，验证合并规则的精确率/召回率，再上。
2. 或在 whisper prompt 里强化数字/型号连写倾向（prompt 层，风险更低），但效果不确定。
两者都应先建 eval case 再动，符合项目"Agent/识别改动必须有可复查 eval"的规则。

## 三、语言标签（已在 R4/R29 修复）
此样本文件名标 `.en` 但内容中文——正是 R4（macOS）+ R29（Windows）修复的 bug。**修复只作用于未来产物**（命名关口用 ScriptDetector 校正）；这个已存在的旧文件名不会被回改（不动用户已有文件是正确的）。未来同类视频的产物将正确标 `zh-Hans`。

## 四、数字拆分只读 EVAL（量化"合并规则"是否值得做）
对"数字 空格 数字 → 拼接"这个直觉修法做了只读评测，结论：**不值得作为简单规则实现，精确率过低会引入事实性错误，比现状（可见空格）更糟。**

### 4.1 影响面（内容相关，非普遍问题）
跨本机 8 个真实样本统计数字拆分：**华为样本 113 处，Spotify 样本 1 处，其余 0**。数字拆分高度集中于"CJK + 密集型号数字"的科技评测内容（麒麟9030/9020 反复出现），不是通用缺陷。英文演讲/音乐样本几乎不受影响。

### 4.2 朴素合并规则精确率（华为样本 113 个数字对分类）
| 类别 | 数量 | 占比 | 简单拼接结果 |
|---|---|---|---|
| 型号类（麒麟/马良 90 30→9030） | 69 | 61% | 大概率正确 |
| **会被拼错（小数/独立测量值）** | 25 | 22% | **错误** |
| 歧义（需上下文） | 19 | 16% | 不定 |

**朴素规则精确率乐观上界 ≈ 73%（69/94），实际更低**（未计歧义类误伤）。

### 4.3 误例分类（为何简单拼接危险）
- **小数被毁**：`2 75 GHz`→应 2.75，拼成 275；`1 72 G`→1.72；`4 9 W`→4.9；`42 1 度`→42.1；`0 7 W`→0.7。这些拼接后是**事实性错误**（275GHz vs 2.75GHz）。
- **型号应拼**：`90 30`→9030、`90 20`→9020、`9 35`(马良)→935、`9 000`→9000、`57 50 mAh`→5750、`6 000 mAh`→6000。
- **合法分隔勿动**：`1 3 4 的 8 核`（计数）、`5490 30 Pro`（跨型号边界）、`7 20 P`/`8 64 P`（DPI 类测量值，歧义）。

### 4.4 风险判断与建议
- **不建议**做朴素 `\d+ \d+→拼接`：22–27% 会把正确的小数/测量值改成错误数字，字幕正确性净负。可见空格是轻微观感问题，错误数字是硬伤——**修法比问题更糟**。
- **理论上**可做单位感知的合并（GHz/W/度/瓦→小数点；麒麟/马良/天玑/mAh→拼接），但：规则复杂、locale 相关、维护成本高、仍有歧义类兜不住，而收益仅限极少数科技评测视频。**性价比低**。
- **更低风险的替代方向**（若日后想改，非本轮，且属算法层需七月决策）：在 whisper prompt 层加型号/数字连写倾向（prompt 引导，不做事后拼接，无"毁小数"风险），效果需 eval 验证。
- **本轮结论**：数字拆分是真实但**低频、内容相关、无低风险修法**的识别层瑕疵。作为已知限制记录，不进入算法改动。时序/分段质量（第一节）才是字幕体验的主要决定因素，且已达标。

## 验收方式（可复现）
```bash
SRT="<样本路径>"
# 时序/分段指标：条目数 + 解析 --> 时间戳算时长/间隔/重叠
grep -cE '^[0-9]+$' "$SRT"
# 数字拆分计数（本样本 113；跨样本对比见 §4.1）
grep -oE '[0-9]+ [0-9]+' "$SRT" | wc -l
# 跨所有真实样本对比数字拆分分布
find ~/Downloads/Moongate -name '*.srt' | while read f; do \
  n=$(grep -oE '[0-9]+ [0-9]+' "$f" | wc -l | tr -d ' '); \
  [ "$n" -gt 0 ] && echo "$n | $(basename "$f")"; done | sort -rn
# 误例分类（型号 vs 小数 vs 歧义）：按后接单位(G/W/度/GHz)判小数，前缀(麒麟/马良)判型号
grep -oE '[0-9]+ [0-9]+ ?(G|W|度|GHz|瓦|分)' "$SRT"  # 简单拼接会毁掉的小数候选
```

## 停机依据（本 eval）
数字拆分是**真实但低频（内容相关）、且无低风险修法**的识别层瑕疵：朴素合并精确率 ≤73%、22% 会引入事实性数字错误；单位感知合并复杂低性价比；更优的 prompt 层方向属算法层需七月决策。**不进入本轮自主改动**，作为已知限制 + eval 证据记录。字幕体验的主决定因素（时序/分段）已客观达标。
